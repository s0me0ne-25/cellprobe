## Правила работы агента

### Процесс
1. Перед началом шага: `git pull`, перечитать ТЗ, глоссарий и этот план из папки `claude/` репозитория.
2. Работа идёт только в рамках текущего шага. Если по ходу выясняется, что ТЗ надо менять, сначала обсудить с пользователем, затем обновить ТЗ.
3. Перед выдачей патча:
   - `./gradlew :core:test assembleFdroidDebug assembleGithubRelease lint`;
   - сборка без новых предупреждений компилятора;
   - lint без новых замечаний в нашем коде.
   - `git diff --check` без замечаний (лишние пробелы в конце строк).
4. **Выдача:** патч файлом (`git diff --binary`, без коммит-сообщения и метаданных git), коммит-сообщение — блоком кода в чате, в конце `Co-Authored-By: Claude <модель> <noreply@anthropic.com>`. Ссылок на сессии нет.
5. Вместе с патчем — чек-лист проверки на устройстве для этого шага (берётся из плана и уточняется).
6. После коммита пользователем: обновить статус в этом плане (патчем, как и любую правку документов).
7. **Документы.** Главная копия ТЗ, плана и глоссария — папка `claude/` в репозитории. Правки документов выдаются патчем вместе с остальными; после коммита копии в проекте claude.ai обновляются из репозитория.

### Код
- Комментарии, идентификаторы, коммит-сообщения — только на английском.
- Тексты интерфейса, README и коммит-сообщения — по `claude/GLOSSARY.md`: позитивная терминология, единое написание терминов. Новый термин сначала дописывается в глоссарий.
- В начале каждого файла: `SPDX-License-Identifier: GPL-3.0-or-later`.
- **`:core`** — только чистый Kotlin без Android: модели, санитайзер, классификатор, стабилизатор, форматирование. Всё здесь покрывается JVM-тестами.
- **`:app`**, пакеты:
  - `data` — DataStore, репозитории;
  - `probe` — сетевой слой;
  - `engine` — цикл проверки, сервис, планировщик;
  - `notify` — уведомления;
  - `ui` — Compose-экраны;
  - `system` — обёртки над API Android: сеть, телефония, пакеты.
- DI ручной, через `AppContainer` в `Application`. Без Hilt и Koin.
- Новые зависимости — только через `gradle/libs.versions.toml`, только открытые и без GMS.
- Никогда не логировать и не сохранять сырые vless-ссылки, UUID, ключи.
- Код, зависящий от канала распространения, — только в `src/fdroid` / `src/github`.

## Шаг 1. Хранилище настроек и редактор списков

**Цель:** пользователь редактирует списки 1, 2, 4 и ЛК, изменения сохраняются.

**Состав** (§2, §2.1, §9.2):
- `:core`:
  - модель записи ресурса (URL, необязательный маркер, флаг `allowRuCa` — пока всегда `false`);
  - модель списка с флагом `customized`;
  - пресеты списков 1, 2, 4;
  - правила: нельзя сохранить пустой список 1/2/4, «сброс на пресет», автообновление пресета для неизменённых списков;
  - нормализация и валидация URL (только `https`).
- `:app`:
  - DataStore для настроек;
  - навигация: главный экран (пока заглушка статуса) → настройки → редактор списка;
  - строка записи `domain.tld [✏️] [❌]`, диалог добавления и редактирования (URL + маркер), кнопка «Сброс на пресет» у списков 1, 2, 4;
  - `AppContainer`.
- **Инфраструктура:** GitHub Actions — тесты, lint, отладочная сборка на каждый push и PR.

**JVM-тесты:** пресеты, правило пустого списка, сброс, автообновление (список не менялся → новая версия пресета применяется; менялся → нет), валидация URL.

**Принятые решения при реализации:**
- Изменения сохраняются сразу после каждого действия. «Нельзя сохранить пустым» реализовано как запрет удалить последнюю запись списка 1/2/4, с сообщением.
- Список, который правками вернули ровно к пресету, снова следует пресету.
- Хранение: typed DataStore + kotlinx.serialization (JSON), файл `files/datastore/settings.json`.
- Навигация — свой маленький back stack без библиотек навигации.
- Маркеры у пресетов пустые; в шаге 3 решено, что они и не нужны.

**Проверка на устройстве:**
- [ ] Списки 1, 2, 4 при первом запуске содержат пресеты, ЛК пуст.
- [ ] Добавить, изменить, удалить запись; после перезапуска приложения изменения на месте.
- [ ] Удалить все записи списка 1 → сохранить нельзя, видно понятное сообщение.
- [ ] «Сброс на пресет» возвращает исходные записи.
- [ ] `http://` и мусор в поле URL отклоняются.

## Шаг 2. Список VLESS и санитайзер

**Цель:** пользователь вставляет vless-ссылку, в приложении остаётся только то, что разрешено ТЗ.

**Состав** (§2.2):
- `:core`: парсер `vless://` → `host`, `port`, `sni`, `fp`, метка. Поддержка IPv6 в скобках, URL-декодирование метки, разбор ручного формата `host:port sni [fp]`. Принимаются строго `security=reality|tls`, остальное и неподдерживаемые транспорты — ошибка.
- `:app`:
  - редактор списка 3: строка «метка — host:port (sni)» с ✏️ и ❌;
  - перехват вставки до попадания текста в поле;
  - поля: без подсказок клавиатуры и без её обучения;
  - редактирование метки.

**JVM-тесты:** реальные форматы ссылок от v2rayNG, Hiddify, NekoBox, Happ (с анонимизированными значениями); IPv6; отсутствие `sni`; мусорный ввод; гарантия, что UUID, `pbk`, `sid` не попадают в результат ни в каком поле.

**Принятые решения при реализации:**
- Диалог: одно поле «Сервер» (ссылка или `host:port sni [fp]`) и поле «Название». Перехват — через `InputTransformation`: изменение с `://` откатывается, поля заполняются результатом разбора.
- Принимаются строго `security=reality|tls`; всё остальное, включая отсутствие параметра и устаревший `xtls`, — ошибка «Поддерживаются только протоколы безопасности tls и reality». Режим не хранится. UDP-транспорты и другие схемы — тоже ошибка.
- Самоподписанные сертификаты не поддерживаются; отсекаются строгой проверкой сертификата на шаге 4 (§5.2), не при вводе.
- Флаги клавиатуры — через `InterceptPlatformTextInput`.
- Разбор адресов вынесен в общий `core.net.Hosts`, его используют и URL-, и VLESS-парсер.

**Проверка на устройстве:**
- [ ] Скопировать ссылку из своего VPN-клиента, вставить → видны только host:port, sni, fp, метка.
- [ ] То же, но вставить в поле «Название» — результат такой же, ссылка в поле не появляется.
- [ ] Файл `files/datastore/settings.json` (Device Explorer или `run-as`): в нём нет UUID и `pbk`.
- [ ] Ручной ввод `1.2.3.4:443 www.example.com chrome` принимается.
- [ ] Ссылка с `security=none`, `security=xtls` или без `security` → «Поддерживаются только протоколы безопасности tls и reality», поле не меняется.
- [ ] Вставка `trojan://…` → ошибка про схему.
- [ ] Повторная вставка той же ссылки → «уже есть в списке».

## Шаг 3. Проверка HTTPS-ресурсов вручную

**Цель:** кнопка «Проверить сейчас» опрашивает списки 1, 2, 4 и ЛК и показывает результат по каждому ресурсу.

**Состав** (§5.1, §5.3, §5.4, §5.5):
- `:app/probe`:
  - OkHttp + Conscrypt, свой клиент на каждый цикл, без пула и кэша;
  - имитация WebView: UA из `WebSettings.getDefaultUserAgent` с кэшем и сбросом при обновлении WebView, заголовки `sec-ch-ua*`, `sec-fetch-*`, `Accept*`;
  - декодеры `br` и `zstd`, набор шифров как у Chrome, ALPN;
  - `network_security_config` с дополнительными корнями (ISRG Root X1 и др.);
  - редиректы не проходим, маркер ищем в первых ~8 КБ тела, таймауты 5/5/10 с;
  - отображение исключений в коды `DNS_FAIL` … `CONTENT_MISMATCH`;
  - параллельный опрос списков; внутри списка первый `OK` отменяет остальные запросы; ЛК опрашиваются все; если весь список не ответил — одна перепроверка.
- `:app/ui`: экран результатов — по спискам: ресурс → код → время ответа.

**JVM-тесты:** отображение исключений в коды результата (на синтетических исключениях), логика отмены внутри списка (через фейковый Prober).

**Принятые решения при реализации:**
- Логика опроса списков, классификация ошибок по фазе, заголовки WebView и разбор страницы — в `:core` (`core.probe`), под JVM-тестами.
- Сетевой слой — `:app/probe`; интеграционные тесты на MockWebServer (на JVM-стеке TLS вместо Conscrypt): все коды, кроме `TCP_TIMEOUT`, распаковка gzip/deflate/br, отмена.
- Conscrypt не глобальный провайдер (§5.1); zstd через `zstd-kmp` со своим правилом R8.
- Код `SKIPPED` для отменённых записей списка.
- Ручная проверка читает тело всегда и показывает `<title>` — по нему подбираются маркеры.
- Маркеры у пресетов не нужны (ТЗ §2.1): валидный сертификат уже подтверждает сайт, а маркер даёт ложные срабатывания.

**Проверка на устройстве:**
- [ ] Обычная сеть (Cellprobe в исключениях VPN): списки 1 и 2 — `OK`, список 4 — ошибки.
- [ ] VPN без исключения для Cellprobe: список 4 — `OK`.
- [ ] Авиарежим: везде `DNS_FAIL` или `TCP_*`, приложение не падает.
- [ ] Маркер, которого заведомо нет на странице → `CONTENT_MISMATCH`.
- [ ] Wi-Fi и мобильная сеть — обе работают.
- [ ] Поворот экрана во время проверки — проверка продолжается, не перезапускается; повторный вход на экран — новая проверка.
- [ ] Заголовки запроса: покрыты юнит-тестом; сверка с настоящим WebView на устройстве отложена до журнала (шаг 6).

## Шаг 4. Проверка VLESS-входов (подмена SNI)

**Цель:** «Проверить сейчас» показывает состояние каждого VLESS-входа.

**Состав** (§5.2, §5.3):
- свой DNS-резолвер, возвращающий для `sni` IP прокси (или результат резолва домена прокси);
- заголовок `Host` без порта;
- переходы только по редиректам того же хоста и порта (до 5), редирект на другой хост не проходим;
- best-effort набор 32 КБ в одном соединении: редиректы, затем повторные `GET` итогового адреса (до 8, не дольше 10 с); счёт байтов на уровне сокета;
- доступен = завершённое TLS-рукопожатие со строгой проверкой сертификата (как у остальных списков, без Минцифры); самоподписанный или не совпадающий с SNI — `CERT_INVALID` (§5.2);
- коды `OK`, `STALLED` (больше 5 с без данных после начала передачи), `OK_UNVERIFIED` (меньше 32 КБ, в том числе сервер закрыл соединение после рукопожатия);
- результаты списка 3 в том же экране, `OK_UNVERIFIED` с пометкой «обрыв не проверен».

**JVM-тесты:** правило «тот же хост» для редиректов, счётчик байтов, выбор вердикта по сценариям (набрали, встали, закончилось раньше).

**Принятые решения при реализации:**
- Списки обобщены: `CheckListId` (1, 2, VLESS, 4, ЛК) и `ListProbing` для любого типа записей. VLESS-входы, как и ЛК, опрашиваются все — иначе состояние каждого входа не показать (ТЗ §5.5 уточнено).
- Подмена SNI — через свой `Dns` на каждый вход: имя SNI резолвится в адрес прокси, любое другое имя — ошибка. Он же разрешает только одно соединение: повторный резолв означает, что сервер закрыл первое соединение, и набор объёма заканчивается.
- Байты считаются обёрткой над потоками обычного сокета. Conscrypt для этих соединений переключён на engine-сокет (`Conscrypt.setUseEngineSocket`): по умолчанию он читает дескриптор сокета напрямую, мимо потоков.
- Время: одна граница 10 с на всю проверку входа, каждому запросу — остаток через `Call.timeout()`.
- После рукопожатия `STALLED` — только таймаут чтения; сброс, закрытие, не-HTTP — `OK_UNVERIFIED` (TLS-вход без fallback ведёт себя именно так). Правила — в `core.probe.VlessProbeRules`.
- Редиректы проходим только до начала повторов; после 5 переходов повторяется последний адрес.
- В диагностике у VLESS-входа видно, сколько КБ получено.
- Закрытие TLS-соединений (`evictAll`) — только на IO-потоке: engine-сокет Conscrypt при закрытии отправляет close_notify, на главном потоке это `NetworkOnMainThreadException`, которое обрывало всю проверку (найдено по logcat на устройстве).
- Исключение, на котором остановилась проверка, сохраняется в `ProbeOutcome.errorDetail` для журнала (шаг 6); в интерфейсе не показывается.

**Проверка на устройстве:**
- [ ] Рабочий Reality-вход → `OK` (или `OK_UNVERIFIED` с пометкой).
- [ ] TLS-вход без fallback (если есть) → `OK_UNVERIFIED`, а не ошибка.
- [ ] Прикрытие с маленькой страницей или редиректом на другой хост → `OK_UNVERIFIED`, в диагностике видно, сколько КБ получено.
- [ ] Заведомо неверный IP → `TCP_TIMEOUT`.
- [ ] Неверный `sni` при правильном IP → `CERT_INVALID` (или `TLS_FAIL`).
- [ ] Если в сети есть известный «обрыв после 16 КБ» — `STALLED`. Если нет, проверяется в поле.

## Шаг 5. Оценка состояния сети и классификатор

**Цель:** «Проверить сейчас» выдаёт итоговый статус по лестнице ТЗ.

**Состав** (§3, §4):
- `:app/system`:
  - активная сеть и её тип (Wi-Fi / мобильная);
  - авиарежим, мобильные данные вкл/выкл (ветки для 26+ и 24–25);
  - флаг портала.
- `:core`: классификатор — чистая функция, все строки лестницы и особые случаи §4.1. `NO_SIGNAL` и `VOICE_ONLY` пока не определяются (шаг 13).
- `:app/ui`: главный экран — статус, текст из ТЗ, тип сети, время проверки, кнопка «Проверить сейчас».

**JVM-тесты:** таблица всех комбинаций «доступен / нет» для списков 1–4 и ЛК, пустые списки 3 и ЛК, `USER_OFFLINE`, `AUTH_REQUIRED` имеет приоритет.

**Проверка на устройстве:**
- [ ] Обычная сеть, Cellprobe в исключениях → `NORMAL` (или `NORMAL_NO_VLESS` при пустом списке 3).
- [ ] VPN без исключения → `LEAK`.
- [ ] Список 3 из одних неверных адресов → `VLESS_BLOCKED`.
- [ ] Авиарежим без Wi-Fi → `USER_OFFLINE`, проверки не выполнялись.
- [ ] Публичный Wi-Fi с порталом → `AUTH_REQUIRED`.
- [ ] Если повезёт оказаться в зоне белого списка → `WHITELIST` (полевая проверка).

## Шаг 6. Журнал, счётчик трафика, диагностика

**Цель:** видно историю проверок и сколько трафика они тратят.

**Состав** (§5.6, §9.1, §9.4):
- кольцевой буфер примерно на 200 записей: время, тип сети, статус, коды по каждому ресурсу. Без сырых ссылок, VLESS-входы — по метке;
- экран журнала с очисткой;
- счётчик трафика за сутки и за месяц;
- на главном экране:
  - состояние каждого VLESS-входа;
  - строка «трафик Cellprobe идёт через VPN: да/нет» (информационно);
  - подсказка при `CERT_RU_CA` — заготовка, само распознавание в шаге 12.

**JVM-тесты:** кольцевой буфер (переполнение, порядок), сериализация записи.

**Проверка на устройстве:**
- [ ] Несколько ручных проверок → записи в журнале с правильными кодами.
- [ ] После 200+ проверок старые записи вытесняются.
- [ ] Счётчик трафика растёт правдоподобно (сверить с системной статистикой трафика приложения).
- [ ] Строка про VPN меняется при включении и выключении исключения в VPN-клиенте.

## Шаг 7. Роли приложений и запуск рекомендованного

**Цель:** пользователь выбирает приложения для ролей, с главного экрана открывается рекомендованное.

**Состав** (§7.3, §9.2):
- `<queries>` для `MAIN/LAUNCHER`;
- диалог выбора приложения: иконки, поиск;
- роли: VPN-клиент, olcRTC, I2P (одно приложение может занимать несколько ролей);
- `:core`: соответствие «статус → роль / действие» по таблице §7.3;
- кнопка «Открыть рекомендованное» на главном экране. Для `PAY` — список ЛК с открытием в браузере. Для `NO_INTERNET` и `AUTH_REQUIRED` — нужные системные настройки. Роль не выбрана → переход к настройке роли.

**JVM-тесты:** таблица соответствия статусов и действий, укорачивание URL ЛК до хоста (вместе с правилом для одинаковых хостов).

**Проверка на устройстве:**
- [ ] В диалоге видны все установленные приложения, поиск работает.
- [ ] Для каждого статуса кнопка открывает правильное приложение или настройки.
- [ ] Удалить приложение, выбранное для роли → понятная реакция, без падения.

## Шаг 8. Фоновый сервис и периодические проверки

**Цель:** при включённом мониторинге проверки идут сами, текущий статус виден в уведомлении сервиса.

**Состав** (§8, §8.1, §7.2):
- `CheckRunner` — один полный цикл, не зависит от того, кто его запустил;
- foreground service `specialUse` (тип объявляется на 34+) с уведомлением: статус, тип сети, время;
- канал «Сервис»;
- тумблер мониторинга, интервалы для включённого и выключенного экрана с переключением по `SCREEN_ON`/`SCREEN_OFF`;
- планирование пока на `Handler`/корутинах, пока процесс жив. Точные будильники — шаг 9;
- запрос `POST_NOTIFICATIONS` на 33+ при включении мониторинга (минимально, полный онбординг — шаг 9).

**Проверка на устройстве:**
- [ ] Включить мониторинг → постоянное уведомление со статусом, время проверки обновляется по интервалу.
- [ ] Экран выключен → интервал увеличивается (видно по журналу).
- [ ] Выключить мониторинг → сервис и уведомление исчезают.
- [ ] Смахнуть приложение из списка недавних → мониторинг продолжается.

## Шаг 9. Разрешения, Doze, автозапуск, события сети

**Цель:** мониторинг переживает сон, перезагрузку и смену сети.

**Состав** (§3, §8, §9.3):
- онбординг при включении мониторинга: экраны-объяснения и последовательные запросы (уведомления 33+, исключение из оптимизации батареи, точные будильники 31+);
- `setExactAndAllowWhileIdle` + partial wakelock на время цикла; без разрешения на точные будильники — неточные, с пометкой в UI;
- `BOOT_COMPLETED` → запуск, если мониторинг был включён;
- `NetworkCallback`: смена сети, выход из `USER_OFFLINE` (пауза 5–10 с), снятие флага портала → внеочередная проверка.

**Проверка на устройстве:**
- [ ] Онбординг проходит до конца; отказ в любом шаге не ломает приложение, в UI видно, чего не хватает.
- [ ] `dumpsys deviceidle force-idle` → проверки продолжаются по журналу (с точными будильниками).
- [ ] Перезагрузка телефона → мониторинг поднимается сам.
- [ ] Переключение Wi-Fi ↔ мобильная сеть → внеочередная проверка в течение ~10 с.
- [ ] Ночь без зарядки: журнал непрерывный, расход батареи приемлемый (зафиксировать цифру).

## Шаг 10. Стабилизатор и уведомления о переходах

**Цель:** смена статуса порождает уведомление нужной громкости, без спама.

**Состав** (§6, §7.1, §7.2):
- `:core`: стабилизатор — подтверждение с быстрой перепроверкой, `UNSTABLE`, правила громкости, сброс при смене типа сети, особые правила для `LEAK`, `USER_OFFLINE`, `AUTH_REQUIRED`;
- каналы «Ужесточение» и «Смягчение»; одно уведомление о переходах под одним ID;
- на заблокированном экране без адресов;
- `engine`: внеочередная перепроверка через 15 с по запросу стабилизатора.

**JVM-тесты:** сценарии на виртуальных часах — одиночный сбой, подтверждённый переход, «мигание» → `UNSTABLE` → выход, кулдаун громких уведомлений, возврат из `USER_OFFLINE` с тем же и с другим статусом.

**Проверка на устройстве:**
- [ ] Выключить исключение в VPN-клиенте → примерно через 15 с одно громкое уведомление `LEAK`.
- [ ] Быстро щёлкать VPN туда-обратно → одно уведомление «Сеть нестабильна», дальше тихие обновления.
- [ ] Авиарежим туда-обратно → уведомлений нет, если статус не изменился.
- [ ] Каналы видны в системных настройках уведомлений приложения.

## Шаг 12. Сертификаты Минцифры для отдельных записей

**Цель:** запись списка 1 или ЛК можно проверять с доверием к корню Минцифры.

**Состав** (§2.3, §5.4):
- распознавание `CERT_RU_CA` по издателю цепочки;
- кнопка `[👮]` с оверлеем 🚫, диалог-предупреждение, подсветка при `CERT_RU_CA`, сброс при редактировании;
- загрузка с `gu-st.ru`, проверка по зашитому SHA-256 корня, проверка подписи промежуточного; запасной путь — выбор `.crt` вручную;
- хранение в `noBackupFilesDir`, удаление, когда флагов не осталось;
- отдельный `X509TrustManager` + клиент на каждый запрос к такой записи.

**JVM-тесты:** распознавание издателя, проверка отпечатка и цепочки (на тестовых сертификатах), правила сброса флага.

**Проверка на устройстве:**
- [ ] Добавить в список 1 сайт с сертификатом Минцифры (например, один из банковских) → `CERT_RU_CA`, кнопка подсвечена.

- [ ] Тот же сайт, добавленный в список 2 (без кнопки) → по-прежнему `CERT_RU_CA`: доверие не утекло.
- [ ] Отредактировать запись → флаг сброшен.
- [ ] Выключить все флаги → файлы сертификатов удалены (`run-as`).

## Шаг 13. Физическое пропадание сети

**Цель:** по тумблеру отслеживаются «нет сигнала» и «только голосовая связь».

**Состав** (§3):
- слушатель состояния сотовой сети без `READ_PHONE_STATE`; если на конкретной версии без разрешения не обойтись — запрос с объяснением, отказ → менее точный запасной вариант;
- статусы `NO_SIGNAL` и `VOICE_ONLY` в классификаторе; уведомления только при включённом тумблере;
- тумблер с подписью мелким шрифтом;
- две SIM: выбирается SIM для мобильных данных; роуминг с выключенными данными в роуминге не считается `VOICE_ONLY`.

**Проверка на устройстве:**
- [ ] Тумблер выключен: в подвале или лифте статус `NO_SIGNAL` виден, уведомления нет.
- [ ] Тумблер включён: то же даёт уведомление.
- [ ] Отказ в `READ_PHONE_STATE` (если его спрашивали) → функция работает в упрощённом виде, повторных запросов нет.
